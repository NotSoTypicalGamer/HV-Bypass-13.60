# 13.60 kernel text re-dump plan

The existing dumps (`ktext_0.bin` 0-0x2800000, `ktext_2800000.bin` 0x2800000-0x3a00000,
`ktext_5ea0000.bin` 0x5ea0000-0x7fe0000) are missing the **`.bss` gap 0x3a00000-0x5ea0000**
and have **scattered scrambled regions** (incl. the ~2.8 MB header). The offset-hunt passes
could not resolve `acpi_sleep_machdep` / `ACPIGBL_FACS` / `IDT` / `COMMON_TSS` / the hypercall
wrapper because they fall in those missing/scrambled regions.

## Payload
`probe94/textdump.elf` (gpread90v3) — reads the kernel text via GPU-DMA (src-leaf retarget,
bit50, bypasses XOM), writes `/data/ktext_<seg_base>.bin`. It reads the target as a
CONTIGUOUS physical range at `ktext_pa + seg_base + k*0x200000` (2 MB chunks, 20 fresh
victims per run). Config file `/data/gpread90_cfg.txt` = `<seg_base_hex>\n<nchunks>\n<bit50>`.

## What to dump

1. **`.bss` gap** — `cfg = "3a00000\n19\n1"` (0x3a00000-0x5ea0000, 37 MB, 19 chunks).
   This is the IDT/COMMON_TSS region (13.60 `.bss` is at VA >= 0xffffffff82f00000 = image
   offset >= 0x2d00000; the IDT/TSS are above that). Run, FTP off `ktext_3a00000.bin`, and
   check it for the 256-entry IDT (16-byte gate descriptors with handler pointers into text).
2. **Scrambled header** — `cfg = "0\n2\n1"` (0-0x400000, 2 chunks). Re-read the header;
   compare to the current `ktext_0.bin` head. If it comes back clean (prologues), the header
   was a one-shot retarget failure and is now fixed.
3. **Scattered scrambled chunks** — identify them first (scan the dumps for low-prologue
   2 MB chunks), then re-dump just those seg_bases.

## Run procedure (one segment)
```text
# write cfg, deploy, pull result
python3 - <<'PY'
import ftplib, socket, io, time
H='10.0.0.x'
cfg=b'3a00000
19
1
'
f=ftplib.FTP(); f.connect(H,2121,timeout=10); f.login('anonymous','anonymous@')
f.storbinary('STOR /data/gpread90_cfg.txt', io.BytesIO(cfg)); f.quit()
s=socket.create_connection((H,9021),timeout=10)
s.sendall(open('probe94/textdump.elf','rb').read()); s.shutdown(socket.SHUT_WR)
time.sleep(3); s.close()   # send-and-forget (elfldr raw TCP)
# wait ~90s, then pull /data/ktext_3a00000.bin
PY
```
The payload logs to `/data/kex_gpread90.txt`; pull that to see `distinct=`/`prologues=`
per chunk (clean code = low distinct + prologues, ciphertext = ~256 distinct + 0 prologues).

## Caveat
The dump assumes the kernel image is physically contiguous from `ktext_pa`. If the `.bss`
pages sit at a different physical offset than text+0x2d00000, the gap re-dump returns garbage
for the `.bss` portion — then the `.bss` PA must be derived separately (from the kernel CR3
walk on the `.bss` VA, or the KERNEL_DATA PMAP). Verify per-chunk `distinct`/`prologues`
against what the region *should* contain (the IDT is a 4 KB run of 16-byte descriptors, not
function prologues).


## Run 1 result (Oct 12) — `.bss` gap came back WRONG region

Dumped `seg_base=0x3a00000` (19 chunks, PA `0x14a00000-0x16f00000`). The `.text` CR3 walk
failed again (`ktext_pa=0x11000000` fallback). Result: every chunk `distinct=256/256`
(high entropy), zero-fraction 31-75%, scattered prologues (0-323) — a **mixed** region, NOT
the clean IDT/TSS. No 256-entry IDT gate run (strict selector-0x20 scan = 0 gates) in the
new dump **or** in the existing `ktext_2800000.bin` `.bss` band (image offset 0x2d00000 =
file 0x500000-0x700000, 60% zeros).

Conclusion: the `.bss` is **not physically contiguous with the text at the assumed offset**,
and/or it is SME-scrambled. The 0x3a00000 target was also wrong — it was the 7.61-based IDT
offset; the 13.60 `.bss` is at image offset ~0x2d00000 (VA >= 0xffffffff82f00000).

## Fix — walk the `.bss` VA directly

The `.bss` is **normal (non-XOM) memory**, so `cpu_va_to_pa(kernel_cr3, 0xffffffff82f00000)`
should succeed even though the `.text` walk failed. Patch `textdump.c` T-B to walk the `.bss`
VA instead of `KERNEL_TEXT_VA`, and set the DMA base from that PA (per-page if needed). Then
the IDT/COMMON_TSS are read from their true physical location.


## Run 2 result (Oct 12) — `.bss` walk works, but it's SME-encrypted

Walking `kb + 0xe00000` (runtime kdata `0xffffffff88dc0000`) SUCCEEDED: `ktext_pa=0x9bc0000`
(= data PA `0x8dc0000` + 0xe00000, so the `.bss` IS physically contiguous with `.data`).
But all 12 chunks read `distinct=256/256, prologues=0` = **ciphertext**. The `.data` (T-A
self-test) reads PLAINTEXT while the `.bss` reads SME-ciphertext.

Conclusion: the kernel `.bss` (IDT/COMMON_TSS/ACPIGBL_FACS) is **SME-encrypted at rest**.
The GPU-DMA retarget reads raw physical bytes and returns the ciphertext — it can never read
those globals. The CPU path (`kernel_copyout` / DMAP access) decrypts on access, so the
Relapse kernel R/W (WAK1360-Relapse `readU64`) CAN read them as plaintext.

## Next — read the `.bss` via Relapse CPU R/W, not GPU-DMA

Use the Relapse primitive to `kernel_copyout` the `.bss` band (VA `kdata + 0xe00000`..) and
scan for the IDT (256 x 16-byte gates) / COMMON_TSS / `ACPIGBL_FACS`. This is a CPU read, so
SME decrypts transparently.


## Run 3 (bssscan via kernel_copyout) — CPU read does NOT decrypt; IDT/TSS are HV-encrypted

Read kdata+0xe00000..0x1e00000 via `kernel_copyout` (CPU path). Per-MB entropy:
- MB 0-1 (.data tail): entropy 7.3-7.9, structured (incl. a 16-byte block
  `0000000000000000 887d6b89 ffffffff` x260 — a pointer table w/ kernel ptr 0x896b7d88).
- MB 2-5 (kdata+0x1000000..0x1400000, 4 MB): entropy 8.00, 0% zeros = **pure AES-XTS ciphertext**.
- MB 6-15: entropy 0.4-3.6, 66-97% zeros = the uninitialized .bss.

Conclusion: the kernel's sensitive .bss (IDT / COMMON_TSS / ACPIGBL_FACS) lives in the 4 MB
ciphertext block (MB 2-5). `kernel_copyout` returns the RAW ciphertext — the HV does the
decrypt on its own (interrupt-delivery) path, not on guest CPU access. So **neither GPU-DMA
nor CPU copyout can read the IDT/TSS**. The `#GP`-via-FACS trigger (needs IDT_GP + IST stack)
is therefore dead on 13.60.

Path forward: drop the #GP trigger; use the Relapse kcall (`worker_rop.fcall`) to call
`acpi_sleep_machdep` directly (no IDT/TSS needed). That still needs the `acpi_sleep_machdep`
VA from the scrambled text region — the remaining text re-dump target.
