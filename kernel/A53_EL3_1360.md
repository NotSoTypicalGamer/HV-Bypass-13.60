# A53 EL3 primitive — VERIFIED on 13.60 (2026-10-06)

## Status: DECI5S/sdbgp A53 read/write WORKS on 13.60 (deterministic)

Deployed `probe93/a53verify.elf` (port of cragson/a53-code-exec to `<ps5/kernel.h>`,
patch-target table skipped) on the live 13.60 console:

```
[+] FW: 0x13600000
[+] mp4sc=0xffffc4e60193d000 zcn_bar2=0xffffc4e6e0400000
[+] state=... flags=... buf=...
[*] version string: "cex(1.1.2.01):Oberon-KDE 2026/07/17 02:22 releases/13.60 229358"
[*] a53_read(0x0)    val=0x0001001000051a00   (A53 boot vector)
[*] a53_read(0x1000) val=0x2a1f03e0910063a2   (ARM64 code)
```

This is **EL3 code execution / read-write, NOT gated by the NPT lucky-boot coin flip**
and NOT gated by the IOMMU that blocked the GPU-DMA sweep at ~2 GB. It is the
deterministic path to HV defeat.

## What changed on 13.60 vs the cragson PoC (≤11.60)

The A53 **L2 page table is no longer at `0x88001000`** — that read returns empty
(`response len=0`), as do `0x1c000000`, `0x60000000`, `0x80000000`.

`a53_read` with `MEM_TYPE_PA_TO_EL3 (0x020000)` reads the A53's **own** physical space
(SRAM/ROM at 0x0). Reaching the x86 DRAM (where the VMCB host-PA lives) needs the A53's
DRAM aperture / EL3 page-table walk, whose base moved on 13.60.

## HARD BLOCKER (13.60): sdbgp memory access is locked to read-only ROM

Live-tested on 13.60 (probe93/a53w2.elf, a53v2.elf, a53rd.elf, mp4mbox.elf):
- `READ_MEMORY` returns data ONLY for the SRAM/ROM `0x0–0x100000` (real ARM64 code). The
  a53.elf at PA `0x88022000` (GET_MMU [01], VA 0x122000), every SYSHUB window
  (0x18000000, 0x4000000, ppr-patch G6 addrs 0x04e27000/0x06000000), and the MMIO all
  return `response len=0`. Setting the `sequence_no` (0x30) and the computed `code`
  field correctly did NOT change this.
- `WRITE_MEMORY` sends (ack'd) but does NOT land on the SRAM/ROM: bit-flip writes to
  0x1000/0x2000/0x4000/0x8000/0x10000/0x20000 all read back unchanged (ROM).
- The fail0verflow "Via x86 Kernel" direct C2P mailbox read (cmd `0x20400000`, regs
  `zcn_bar2+0xF6000/0xF7000/0xF8000/0xF9000`, plus `mp4_softc+0x160/0x164` and the `ack`
  reg, even with `/dev/mp4/dump` held open + ioctl START) NEVER completes — the `cmd`
  register never clears, so the A53 does not process the direct read command on 13.60.

So ALL THREE A53 memory paths are dead on 13.60: the cragson/ppr-patch code-exec route
(read a53.elf in DRAM → patch sdbgp context handler → icache flush) needs DRAM reads +
SRAM writes that 13.60 denies, and the direct C2P read that fail0verflow used on ≤4.51 is
gone. **The A53 lane is closed on 13.60.**

**Next lead:** none via the A53. Remaining VMCB routes are the CPU root-0 NPT "lucky boot"
(unproven) and the GPU-DMA READ/WRITE (IOMMU-gated at ~2 GB). See skill for both.

## GET_MMU result (13.60, 2026-10-06)

`SDBGP_GET_MMU` (0x1200021) returns the A53 **EL1** translation map — 28 entries on 13.60.
Decoded from `/data/kex_a53mmu.bin` (response header @0x60, mmu-reply @0xa0, results @0xd0,
each result 0x30 bytes: mpt_el u8@+4, vbase@+8, length@+0x10, pbase@+0x18, attr@+0x20, psz@+0x28):

- [00] VA 0x1000–0x10000 → PA 0x1000 (SRAM, identity)
- [01] VA 0x122000–0x126000 → PA **0x88022000** (a53.elf .text)
- [10] VA 0x3a00000 → PA 0x88700000 ; [16] VA 0x40b6000 → PA 0x880e0000 (more a53.elf)
- [07] VA 0x3000000 → PA 0xf6e00000 ; [12] VA 0x4001000 → PA 0x48800000 (PSP DRAM)
- [26] VA 0x28000000 → PA 0x18000000 (32 MB) ; [27] VA 0x28800000 → PA 0x18800000

Highest PA in the map ≈ 0xf6e00000 (3.85 GB). The A53's physical space is its OWN memory
(SRAM + PSP DRAM carve-outs), **separate from the x86's guest-PA (0–16 GB) and host-PA
(32–40 GB)**. The a53.elf lives at PA ~0x88022000 (2.1 GB), which is why the old
`A53_L2_TABLE_PA = 0x88001000` and a naive 8 MB-step scan of 2–4 GB "found nothing" — the
DRAM is sparse (0x88022000 / 0x880e0000 / 0x88700000), not contiguous.

## mem_type enum (authoritative, from astrelsky/mp4rw include/mp4.h)

- `PA_TO_EL3_VA   = 0x020000` — PA → EL3-accessible address (A53 physical space)
- `EL3_VA_TO_EL3_VA = 0x430000` — EL3 VA → EL3 VA
- `EL0_VA_TO_EL3_VA = 0x400000` — EL0 VA → EL3 VA

**There is no S2 / system / SMN mem_type** — the DECI5S READ/WRITE cannot reach the x86
DRAM. Reaching the VMCB therefore requires A53 CODE EXEC (patch the sdbgp context handler,
the write flushes icache) and then SMN/DRAM-controller access from the payload.

## Pitfalls

- Each `a53_read` is a full DECI5S packet round-trip (open/revoke /dev/mp4/dump + ioctl
  + kevent) — seconds per read, so a brute-force full-DRAM scan is impractical; scan
  targeted ranges and poll the log file over FTP.
- The mp4 payload is a long-lived process: re-deploying while a previous scan is still
  running fails `mp4_init` (`Failed to find coredump state/flags (sa=0x0)`). Cold-boot
  between runs, or wait for the previous process to exit.
